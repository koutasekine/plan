# 申し送り書: 計画の比較アプリ(差分アプリ)

作成: 2026-10-26。元の作業: プロジェクト計画(plan.sapp.jp、リポジトリ plan)版 0.29。

## 1. 目的

- ハッカソンの最終報告書で、学生に「プロジェクト計画段階の計画」と「プロジェクト最終時の計画」を比べさせている。今は手動で、書式がばらばらで採点が大変。
- 2 つの .plan を読み、決まった形の比較を出すアプリを作る。学生と教員の両方の手間を減らす。
- 今の運用で使うので、今作る。

## 2. 確定した方針

- プロジェクト計画とは別のアプリにする。プロジェクト計画に入れると、全部の意味が変わってしまうため。
- S Apps の作る基準に従う: 単一 HTML、外部ライブラリなし、データをどこにも送信しない、ネットなしで動く、決定的。
- 計算部(解析と日程の計算)は、プロジェクト計画と同じものを組み込む。記法の直しが両方のアプリに同じく入るようにする。
- 2 つの .plan は、同じ版の計算部で読む。
- 要素は名前で対応づける。名前の変わった要素は「消えた要素」と「増えた要素」の 2 行で出す。
  - 名前の似た要素などを自動で対応づけることはしない(禁止)。
  - 学生に「名前を変えないこと」を指導する前提は置かない。実際の開発でも名前は変わる。
- 比べる内容は次の 1〜5 のすべて。
  1. 概要: 期間・終わりの日・クリティカルパスの長さ・作業の件数・日数の合計を、計画時と最終時で並べる。
  2. WBS の作業: 増えた作業、消えた作業、変わった作業(日数・担当・確認・先行・対象(for)・状態)の一覧。
  3. 日程: 作業ごとの計画の終わりと最終の終わりのずれ。いちばん遅れた作業。
  4. FBS・PBS・MOP: 増えた・消えた機能や部品、増えた・消えた MOP、チェック済みになった MOP。
  5. 担当者: 増減と、担当者ごとの作成の日数の変化。
- 比べる 2 つのファイルの間隔は問わない(1 日ごとでも不定期でもよい)。変更履歴は、日付の入った版を残しておけば比べられる。
- 版の日付は、plan 側の `version:` を使う(版 0.29 で実装済み。仕様書 3.3 節・4.1 節・9 章)。
  - `version:` は最後にファイルとして保存した日(日付だけ、時刻は入れない)。1 行目にだけ、字下げせずに書ける(ほかの場所はエラー)。上書き保存・別名で保存のときに plan が書き、なければ 1 行目に足す。正しくない場所に `version:` があれば、plan は保存しない。
  - 内容が同じなら版も同じ: 1 行目の `version:` の日付の部分(注または行末までの値)だけを除いて 1 文字でも違うときだけ日付を変える(注・空白・行の有無は比べる)。違いがなければ上書き保存は書き込まず、別名で保存は日付を変えずに書き込む。
  - 自動保持・画像の保存・印刷では日付を変えない。手で日付を書き換えることは防がない。
  - 図・日程・検査には使わない。

## 3. 未決事項(作る前に晃太さんの裁定が要る)

- 3 つ以上のファイルを `version:` の順に並べて扱うかどうか(任意の 2 つを選んで比べるだけにするか)。
- `version:` の日付を「今日」として、その日時点の遅れも比べるかどうか。`version:` のないファイルの扱い。
- 比べるときに `version:` の行を違いとして出すかどうか。
- アプリ名と公開先(plandiff.sapp.jp は例として挙げただけで、未決)。リポジトリ名。
- 公開するかどうか。
- 名前の対応づけの単位。今の計算部の `qname` は根からの全部の名前を `::` でつないだもの。
  - 根の名前(プロジェクト名)が計画時と最終時で違うと、すべてが「消えた」「増えた」になる。根を除いた並びで対応づけるか。
  - 親を移した要素(名前は同じ)は、全部の名前で対応づけると 2 行になる。これでよいか。
- 出し方: 1〜5 の表をビューとして並べ、印刷 / PDF でまとめて出す形でよいか。表の列と並び順。
- 「変わった作業」の判定に、`note:` を入れるか。
- どちらかの .plan に構文エラーや検査のエラーがあるときの扱い(比べないで止めるか)。
- 日程のずれの単位(日数か日付か)と、作業日と暦日のどちらで数えるか。
- 2 つのファイルの読み込み方(2 か所への投げ込み、ファイル選択)。保存(autosave)を持つかどうか。

## 4. 残作業

- 上の未決事項を晃太さんに尋ね、裁定を得る。
- 仕様書の案を作り、承認を得てから実装する。
- 組み立ての台本(build.py)で、plan の core.js の計算部を新しいアプリに写す仕組みを作る。

## 5. 使える既存の部品(plan リポジトリ)

- `core.js` の `/*CORE-BEGIN*/` 〜 `/*CORE-END*/` が計算部。画面の処理を使わず Node でも動く。`build.py` が index.html に埋め込む。`test/core_test.cjs` は index.html から計算部を取り出して検査する。
- 公開している関数: `parse, analyze, stripVersion, setVersion, render, printPages, printPortrait, peopleLoad, plannedByToday, workUntil, describe, toPrompt, embedSource, extractSource, VIEWS, STATUS, fmtDays, fmtDate, buildAOA, Edit`。
- `stripVersion(text)`(1 行目の `version:` の日付の部分を除いたテキスト)・`setVersion(text, date)`・`misplacedVersion(text)`(正しくない場所の `version:` の行の番号)も公開している。
- `analyze` の結果 `r`: `r.tasks`(葉の作業。`days` は 1/1000 日単位の整数、`by`・`review`・`status`、`d1` は終わり)、`r.sched`(`start`・`spanDays`)、`r.qname(n)`(修飾名)、`r.sec`(節)、`r.members` など。中身はコードを開いて確かめること。
- 担当者ごとの作成の日数と稼働率は `peopleLoad(r)`、今日までの予定は `plannedByToday(r, today)`。
- 印刷の仕組み(サマリーは縦、他は横、A4 横で 0.5 倍を下回るときは分ける)は `printPages`・`printPortrait` と build.py の印刷用 CSS。
- 仕様書 `docs/spec.md`(版 0.29)。`version:` は 3.3 節・4.1 節・9 章、名前と参照は 3.7 節、日程の計算は 6 章、ビューは 7 章、未決の【提案】は 12 章(P1〜P26)。

## 6. 守ること

- 実データ `team42.plan`(昨年のハッカソンの学生名入り)は、検査やリポジトリに入れない。検査用のデータは架空の名前で作る。
- 記法は簡単なままにする。
- 計算部の規則(12 章の【提案】)は、これからも変わりうる。比較は同じ版の計算部で両方を読むので一貫する。
